# 保护业务约定

服务面向博物馆的藏品、修复和公共服务场景。时间字段统一使用带时区的 ISO 8601 字符串，身份字段使用不可变字符串。所有业务变更都保留经办角色（`actor`）和发生时间（`at`），避免用展示层文本代替结构化状态。

健康检查只用于确认进程存活，不代表任何业务流程已经完成。数据文件落盘在运行时配置（`RESTORATION_DATA_FILE`，默认 `./.runtime/events.jsonl`）指定的位置，测试不得依赖主机上的隐藏状态。

## 修复工单模块的领域约定

### 事件溯源与哈希链

所有业务变更（文物登记、工单、方案版本、会签、批准、工序开完工、冻结、跳过、返工、材料入库/核销/领用、质控）都是只追加的事件，逐行写入 JSONL 日志。每条事件携带：

- `id` / `type` / `at` / `actor` / `artifactId` / `payload`
- `prev`：上一条事件的 SHA-256；首条为 64 个 0
- `hash`：对除 `hash` 外全部字段做键排序规范化后的 SHA-256

服务启动时回放整份日志并重建内存投影，同时校验哈希链；链断裂或 JSON 损坏时拒绝启动，不在被篡改的历史上继续记账。每次写入先 append + fsync，成功后才更新投影。

### 命令串行化

写命令的“校验 → 事件构造 → 落盘 → 投影”整体在同一把 Promise 队列中串行执行。并发领料因此基于上一笔已提交库存做判断，杜绝超卖；一个业务动作（如批准方案）产生的多条事件在同一事务内构造，中途校验失败则一条都不落盘。

### 方案版本化与会签

- 方案变更必须携带结构化 `riskNote`（风险概述、影响工序、应对措施、残余风险），与 `plan_draft_created` 事件绑定，进入时间线。
- 方案经历 `draft → submitted → approved/rejected`；专家会签一人一次留痕，任一驳回即驳回，批准需达到会签人数（≥2，随材料数增加，上限 5）。
- 方案批准时：已开工/已完工/已跳过的旧工序实例保持原样并挂接到新方案；未开工实例冻结并记录冻结原因（绑定变更摘要与风险）与接替实例；新增工序生成待办实例。已开始的工序不能被静默改写。

### 工序、依赖与返工

- 工序状态：`pending / active / done / frozen / skipped`。
- 依赖判定以同编码“最新实例”为准：旧实例完工但已开返工时，下游等待返工实例完工；`skipped` 视为依赖已了结。
- 返工只追加新实例（`rework_opened`），原实例的施工、领料、质控记录原样保留，经 `originInstanceId` / `reworkInstanceIds` 关联。

### 材料

- 入库强制供应商；质检证书缺失的批次允许登记但禁止领用（`batch_origin_unknown`）。
- 领用校验批次存在、未过期、来源证书齐全、库存充足、工序可施工；过期（`batch_expired`）与来源不明一律阻止。
- 领用事件保存批次快照（有效期、供应商、证书号），保证事后追溯到领用当时的批次属性。

### 可追溯责任链与时间线

每条事件的 `actor`/`at`/`prev`/`hash` 构成责任链。`GET /api/artifacts/:id/timeline` 聚合该文物跨工单的全部事件，管理员可导出 CSV。服务恢复后待办、冻结原因、库存余量、会签与返工责任链均从日志重建。
